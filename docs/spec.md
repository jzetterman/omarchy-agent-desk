# Spec — Agent Desk: AI usage and account switcher for Omarchy Quattro

Status: v12.6, 2026-09-03 (US Eastern). Gate: closed (see section 10). Mechanism lives in `design-notes.md`, the plan's design seed. Tier: Full. Owner: John Zetterman.
Plugin id `io.github.jzetterman.agent-desk`.

## 1. Problem

Omarchy users who run more than one AI coding CLI, and sometimes more than one account per CLI, have no single place to answer two questions: "how much headroom do I have right now?" and "which account should my next session use?". The marketplace splits this into usage trackers (the stock `omarchy.agents` panel plus ~40 feeders and clones) and account switchers (acrogenesis, brandonwhitfield). None combine the two, and none reach the finish of the World Clock plugin: deliberate hierarchy, quiet transitions, complete keyboard model, every state designed.

## 2. Goals

1. One bar icon and one panel that show rate-limit headroom for every saved account across Claude Code, Codex, and Grok, and let the user choose the account new sessions use.
2. Finish comparable to World Clock: the shell's own Ui kit and tokens, every status designed, no layout jumps, motion only where it explains a change.
3. Provider support is data plus one collector per provider. Adding OpenCode Go, OpenRouter, or another gateway must not touch the panel.

## 3. Non-goals (v1) and v2 candidates

- Token history (tokens by day, by model, sparklines). v2.
- Desktop notifications when a window crosses critical or a capped window resets. v2.
- Multi-machine aggregation or sync.
- Feeding the stock `omarchy.agents` record directory. Possible later opt-in.
- API-key (pay-per-token) billing. Prepaid balances are supported only through the provider contract.
- Replacing the CLIs' login flows. We always invoke the official login command.

## 4. Definitions

- **Provider**: one CLI described by a descriptor and served by a collector. Launch provider ids are `claude`, `codex`, `grok`. Descriptors and collectors live in a per-provider directory inside the plugin; an extra provider is one more directory there.
- **Home**: the directory a CLI reads its credentials, settings, and state from, selected by that CLI's own environment variable.
- **Default home**: the CLI's normal home: the value of the CLI's home environment variable when set, else the descriptor's declared default path (for example `~/.claude`), expanded at import and recorded as the imported account's home. Owned by the CLI. Agent Desk's own code never writes there. Invoking the CLI's own commands, which may refresh their own tokens, is allowed in any home.
- **Isolated home**: a home Agent Desk created for an added account. Agent Desk owns its credential and account state.
- **Account**: a saved login. Exactly one of: the imported default home, or an isolated home. Has a stable id independent of its name or email.
- **Active account**: exactly one saved account per provider. Command routing (R13) uses that provider's active account. Middle click, IPC `next`, and the header "Open terminal" action (R19) use only the active account of the first provider (R18). Each card's own "open terminal" uses that card's account. When a provider's first account is imported it becomes that provider's active account.
- **Status**: one value per account per refresh, mapped from collector outcomes as follows. `not-installed`: the CLI binary is missing. `not-signed-in`: no interactive-login credential is present (API-key-only files count as not signed in). `expired`: the token is expired (default home; or isolated home when the refresh was not attempted or the grant was rejected). A refresh URL that is unreachable is `offline`, one that returns 429 is `rate-limited`, and any redirect, timeout, 5xx, or malformed answer is `failed`; only grant rejection leads to Sign in again, and all of those take backoff (R6). `rate-limited`: the usage or identity request itself was rejected for throttling (HTTP 429 or equivalent); a window at `used` 1.0 is still `ok` with a full rail. `offline`: the endpoint is unreachable (DNS, no route). `failed`: timeout or any other error. `no-limits`: identity succeeded and the payload has no windows and no balance. `ok`: otherwise. A usage or identity request rejected for invalid authentication (401 or 403) is `expired`. Every record also carries a **status reason**: for `expired` one of `default-home` (only the CLI's login fixes it), `deferred` (isolated home, refresh not attempted this run for a local reason; see design note D1), `grant-rejected` (refresh grant refused), `rejected` (usage or identity request refused), or `unsupported-refresh` (the descriptor has no refresh URL or the grant needs a secret; no request is made, last-known values are kept, no backoff); Sign in again is offered on isolated homes for `grant-rejected`, `rejected`, and `unsupported-refresh`. **Stale** is an orthogonal flag: the record's age exceeds the refresh interval.
- **Window**: one rate-limit allowance: a stable id (collector-supplied, else the normalized kind plus label), a kind (session, weekly, monthly, billing-period, model-scoped), a label, `used` as a fraction in 0..1, and a reset time. Or a **balance** for prepaid providers: remaining always, funded and spent when known, a provider-supplied unit (a currency code or a word such as "credits"; "credits" when absent) and a display precision (0 decimals when absent). A balance exposes `used` as spent/funded when both are known and funded is greater than zero, else 0 while remaining is above zero and 1 when it is zero (never NaN or infinite), so balances take part in highest used. Grok billing-period credits are a `billing-period` window with `used`, not a balance, unless the payload supplies an explicit remaining/funded/spent triple.
- **Highest used**: the maximum `used` across a set of accounts' windows and balances. Used with one meaning throughout.
- **Card order**: within a provider, the imported account first, then isolated accounts in persisted creation order; rename and credential replacement never change it. Middle click, IPC `next`, tie-breaking, and keyboard traversal all use it.
- **Identity match**: same provider id and same normalized email. Normalize by trimming ASCII whitespace and lowercasing the domain; the local part compares case-insensitively and keeps `+` tags. An empty email never matches and is not a usable identity. Org, team, and plan label are display only.

## 5. Users and scenarios

- John: Claude Max (session, weekly, and a model-scoped weekly window), Codex team (weekly only), Grok (billing-period credits). Wants to glance at the bar and know whether he is about to hit a wall, and open the panel for reset times.
- A user with two Claude accounts (personal, work). When personal hits its weekly cap they switch to work for new sessions without disturbing running ones, and switch back when the window resets. The panel makes the decision obvious: which account has the most headroom, and when the capped one comes back.
- A user adding a provider (OpenCode Go). They add one descriptor and one collector; the panel gains the provider with correct mark, windows, statuses, and account handling.

## 6. Requirements

### 6.1 Providers
- R1. Launch providers: Claude Code, Codex, Grok.
- R2. A provider descriptor declares, by role: id, display name, mark (with a light-surface variant), CLI binary, the CLI's home environment variable, login command, logout command if the CLI has one, session launch command, the list of user-configuration entries an isolated home shares with the default home (R8), the list of account-state entries seeded once at add time with, for each, the identity keys to strip before seeding (R8), the declared default home path, the credential file name and how the current interactive entry is selected within it (R4), the CLI's own credential lock file if it keeps one, the temp file names Agent Desk may create beside the credential file, the scale rule for its payloads (R3), and the provider's usage and identity URLs plus an optional token-refresh URL and optional public OAuth client id, all as `https://` constants. Everything provider-specific lives in the descriptor; nothing about a provider is read from a home file, credential payload, or QML, with one exception: a descriptor may name the credential-file key that holds the CLI's own public OAuth client id, for a CLI that stores it there (Grok); the refresh URL itself stays a constant. No client secret exists in v1; a provider whose grant needs one, or whose descriptor omits the refresh URL, never refreshes and reports `expired` with reason `unsupported-refresh`. The descriptor schema is a plan artifact. A collector has two modes: `full` (network, per R6) and `identity` (no network, no refresh, no usage: reads only local credential and account-state files and returns identity or `not-signed-in`). In `full` mode, given a home, it returns one record: identity (email, org or team, plan label), windows or a balance, a status from section 4, and one human help line. Concrete endpoints, transports, and payload fields belong in the plan.
- R3. Collectors normalize. `used` is always a fraction in 0..1. Scale is a per-collector decision from the provider contract (design note D7); payload sniffing is the fallback only for a provider documented to vary. Clamp to 0..1 after conversion. Window kind and label come from the payload's own declarations, never from parsing model names. A window's period (for example Grok's week or month) comes from the payload. Optional per-product percentages, overage, and prepaid balance are carried when present.
- R4. Where a credential file holds several entries, the collector ignores API-key entries and uses the interactive-login entry the CLI itself treats as current (the descriptor names that key); with none marked current it uses the first interactive entry in file order. Entries are never merged.
- R5. Token handling. A collector prefers a path that needs no token handling where the CLI offers one. Otherwise it reads the home's credential file. In the default home the collector never refreshes: an expired token reports `expired`/`default-home` with the CLI's own login command. In an isolated home the collector may refresh an expired token once per run using the provider's documented refresh grant and the descriptor's public client id, holding these invariants (mechanism in design note D1): refresh only when the token has been expired long enough that no live CLI session in that home is plausible; the credential file is never left partial, never above mode 0600, and never loses entries other than the current interactive one; a token obtained from the provider is never dropped (a failed commit leaves a complete recovery file that the next run commits); a concurrent write by the CLI in that home is detected and the refresh is not sent; a refresh not attempted for a local reason is `expired`/`deferred` with last-known values kept and no backoff; a rejected grant is `expired`/`grant-rejected`; other failures take the section 4 statuses and enter backoff. Tokens never appear in logs, output, process arguments, process environment, or QML properties. The README documents the two residuals: a CLI session racing in the same home, and a kill between a sent request and its commit.
- R6. Collectors run outside the shell process, in parallel across accounts, each with a hard timeout of 30 s that also ends any process the collector spawned; a hung collector never blocks its siblings and yields `failed` with last-known values and their age (or, with no last-known record, `failed` with no rails, the help line, and no numeric contribution to the bar). Collection is single-flight per account, and a result that started before a replacement or removal of that account is discarded. Results are cached per account. A manual refresh is honored at most once per 60 s per account; the scheduled refresh interval is a setting with minimum 60 s and default 900 s; opening the panel triggers a refresh subject to the floor. Backoff delays scheduled runs only, per account, after `rate-limited`, `offline`, `failed`, or a failed isolated-home refresh, starting at twice the interval, doubling, capping at eight times, cleared by any successful run or other status; sibling accounts still run; manual triggers ignore backoff. Cached values keep being served with their age. No process ids are persisted or signaled across restarts; exclusion is by per-home locks (design note D2).
- R7. A provider whose CLI is not installed has status `not-installed` with an install hint, never an error. Installed means an unmarked executable resolves through the shim's real-binary rule (R13); a marked shim alone never counts. Install is detected on plugin start and on every runner cycle.
- R7a. The runner and collectors iterate only the saved accounts in plugin state and never discover accounts by enumerating the homes directory; uncommitted trees never contribute to refresh or the bar, and the panel shows them only as the in-progress card of R10. One startup cleanup pass, run only after plugin state loads and validates (if it cannot load, nothing is deleted and the panel shows a recovery error), removes trees that are not saved accounts. A tree with a possibly live login is never deleted: it is quarantined. Mechanism in design note D3.

### 6.2 Accounts
- R8. Any number of accounts per provider. Isolated-home paths in plugin state are never trusted as given (design note D4). The default home of a provider is imported automatically, once, the first time that provider's CLI is detected as installed (R7), as that provider's first account; it records the default home path as its home (shared links and health checks always use that recorded path, never a live re-read of the env variable) and is never copied, moved, or relocated. Isolated homes under `~/.config/omarchy/agent-desk/homes/<provider>/<account-id>/` are created only by adding an account (R10), mode 0700, credential files 0600. Before any operation on an isolated home its path is derived from ids alone and revalidated; anything that is not a plain directory Agent Desk created, holding plain files, fails closed and reports (design note D4). Only credentials and account state are isolated; an isolated home shares the user's provider configuration with the default home. Two classes, both named per provider in the descriptor: **shared entries** (instructions file, settings, skills, plugins, hooks, themes, and conversation history where it lives in the home) are linked to the default home. Before every launch that Agent Desk itself performs (a card's open terminal, the `o` key, the header action), missing shared entries are re-established; an entry that exists but no longer resolves to the default home is never touched automatically. Shared-entry health is computed on each successful collector run and on each Agent Desk launch; drill-in (R24) shows it, and the panel offers to relink, which backs up the diverged copy in place (never overwriting an earlier backup) and recreates the link (design note D4). The routing shim does not manage links. **Account-state entries** that mix identity with configuration (Claude's `.claude.json`, which holds user-scope MCP servers and project trust alongside the login) are seeded once from the default home before login with identity keys stripped; the README lists what therefore does not stay in sync.
- R9. Intentionally unused so requirement ids stay stable.
- R10. "Add account", in this order: create the isolated home (0700); seed account-state entries with identity keys stripped; link shared entries; run the official login command in that home in a terminal Agent Desk controls, owning the login process itself (design note D3). While it runs the section shows an in-progress card with Cancel. Completion means a usable identity in that home from the collector's `identity` mode; a failed login is the owned process exiting with identity still unusable; neither is judged from the terminal launcher's exit. The account is saved only after that; default name is the account email. If the identity matches an existing isolated account, the panel offers to replace that account's credentials (keeping its id and name): on accept, the replacement is atomic, replaces only the current interactive entry, never overwrites a newer token the CLI wrote meanwhile, and leaves the target untouched on any failure (design note D5). A successful login or replacement invalidates that account's cached record before state is published and triggers one full refresh that bypasses the floor, showing loading meanwhile. If it matches the imported account, the panel says so and points to the CLI's own login. A login in progress survives panel close (the shell closes the panel on the first click outside it, which every login needs); its in-progress or decision card returns when the panel reopens. On explicit cancel, failed login, decline, discard, or the pending cap, the owned login process is stopped first, then the uncommitted fresh tree is deleted without running logout; if the process cannot be verified gone the tree is quarantined (design note D3). It never stays on disk as a live home.
- R11. Card actions: rename; "Sign in again"; remove. "Sign in again" runs the login command in that account's home and keeps id and name; for the imported account it runs the CLI's own login in the default home. Sign in again on an isolated home runs the login in a fresh 0700 staging home prepared exactly as in R10 (this account's home is never touched during login) and presents the same in-progress card; after a usable identity, if it matches this account, the credentials and the descriptor-declared identity keys of account-state entries are committed into this account's home with the R10 transaction guarantees, configuration keys preserved; a new identity is rejected for this flow with a pointer to Add account; if it matches another isolated account, offer Replace (commit into that account instead, keeping its id and name) or Abort; if it matches the imported account, abort and point at the CLI's own login. Every unsuccessful outcome (cancel, failed login, abort, the pending cap) deletes the staging home as in R10 and leaves this account unchanged; panel close does not end a login. No two saved homes ever hold the same credentials. Remove requires confirmation, runs the CLI's logout command in that home when the descriptor has one (logout runs only here, never on uncommitted homes, and is best-effort: a non-zero exit is shown on the panel caption until the panel closes, for example "Codex logout failed · work still removed", and the tree is still deleted; logout is bounded by the collector timeout), then publishes one atomic state update that removes the account and, if the removed account was active, selects the imported account as active, and only after that deletes exactly that isolated home's tree and purges that account's records and caches without touching siblings (a crash between the two leaves an orphan that R7a cleans). When two cards of one provider hold the same identity (the imported home later signed into an isolated account's identity), both are marked "same account as <name>" and Remove warns that the provider session may be shared. Removing the active isolated account makes the imported account active; removing a non-active account leaves the active account unchanged. The imported account's pencil menu omits Remove and any other remove path is refused; it can only be hidden by the per-provider enabled setting, which hides that provider's whole section; per-account hiding is v2.
- R12. Setting the active account is one click or keystroke, idempotent, and reversible with the same gesture on the previous card. Plugin state is published atomically (a reader sees the complete old or complete new state, never a partial write), and the announcement follows the publication. The panel caption announces it and replaces the live caption until the panel closes: "Codex → work for new terminals" when routing is on, "Codex → work for Agent Desk terminals" when routing is off. Whenever routing is off, independent of any announcement, the header shows one muted line "Routing off" with the install action. Running sessions are never touched.
- R13. Ways to use accounts: (a) each card's "open terminal" opens the user's configured terminal with the CLI running in that card's home; the header's terminal action uses the active account of the first provider (R18); always available. (b) Optional command routing: plain `claude`, `codex`, `grok` in any new terminal follow the active account. Routing is off by default, installed by one explicit action, removed by one action, and defers to an explicitly set home variable in that shell. Invariants (mechanism in design note D6): the shim is self-contained and marked; it never execs another marked file and never keeps a recorded path; an explicitly set home variable in the shell always wins; a home is applied only on an exact canonical match with that provider's imported home or the isolated home of the saved account id, by setting the home variable in the child environment (tokens never in env or argv), except that for the imported account whose default home was not selected by that variable at import, the real CLI runs unchanged, because setting the variable to the CLI's own default can relocate its state files; missing, unreadable, or malformed state, or any other path, runs the real CLI unchanged; the only fail-closed cases are "no unmarked binary exists" and "valid state names a saved isolated account whose home directory is missing", both exiting non-zero with a short message; a missing imported default home runs the real CLI unchanged, because the CLI must be able to create its own home on a fresh machine. Install creates one shim per currently installed launch-provider binary (a later-installed CLI gets its shim on the next runner cycle while routing is on), never replaces an unmarked file (it refuses as a whole and writes nothing), and is all-or-nothing. Removal deletes marked shims and Agent Desk's PATH change, leaves unmarked files untouched, and reports them. After install, plain `<binary>` in a new interactive login shell must resolve to the shim for every provider a shim was created for; install verifies this per provider and reports any provider whose shim is shadowed, naming the shadowing PATH entry, and routing is then reported as partial, not on. How Agent Desk wins PATH precedence is a plan decision. On plugin disable, any surface that still renders and the README name the routing-removal action when a marked shim remains; after uninstall only the README applies.
- R14. Usage is fetched for every saved account, not only the active one.

### 6.3 Bar widget
- R15. The icon is always visible once the plugin is enabled. With no provider CLI installed, the panel shows the `not-installed` state with install hints.
- R16. Beside the icon, a compact readout of the highest used across the accounts in scope (setting `readoutScope`: `active` default, or `all`), shown as an integer percent rounded half up from `used × 100` while thresholds compare the raw fraction, colored by threshold: warning when highest used is at or above the warning threshold (default 0.75), critical when at or above the critical threshold (default 0.90), critical wins; both thresholds are settings. The readout can be switched off. When no account in scope has a numeric `used`, the readout is omitted and the icon carries no threshold color. On a vertical bar the readout is omitted and the icon alone carries the threshold color. A stale contributing record still drives the percent and color.
- R17. Hover tooltip names the plugin and the highest used item. For a window: "Codex · work · weekly 81% · resets in 5d 2h". For a balance: "Grok · default · remaining 6", with "· 40% used" appended when `used` came from spent and funded. Both append "stale · 20 min ago" when stale. Ties on `used` resolve by provider order, then card order, then kind order (R21). One countdown formatter is used everywhere: the largest two units down to minutes; a future reset under one minute reads "1m", never "0m" or a negative span.
- R18. Left click toggles the panel. Right click refreshes. Middle click cycles the active account of the **first provider**, defined once here as the first enabled and installed provider in the configured provider order; when there is none, middle click and the header action (R19) do nothing and the header action is hidden. Middle click and IPC `next` wrap in that provider's card order. Right click and IPC `refresh` request every saved account subject to the 60 s floor. IPC verbs: open, close, toggle, refresh, next.

### 6.4 Panel
- R19. Content width 380 px; height capped at 640 px via the shell's fitted content height as the stock agents panel does; long lists scroll inside the panel. Header: caption line with live context ("3 accounts · refreshed 2 min ago", or the announcement from R12), title with the mark set between the two words in the World Clock style, and a header action "Open terminal" for the active account of the first provider (R18).
- R20. One section per provider: every launch provider plus any installed extra descriptor, in the `provider order` setting (default Claude Code, Codex, Grok), with providers not named in the setting appended in descriptor-id order. A provider with `enabled: false` has no section, its collectors do not run, and its accounts are excluded from the bar, tooltip, middle click, and `readoutScope: all`. An enabled provider whose CLI is not installed still shows its section in the `not-installed` state (install hint, no cards); R15's empty state is that view. If no section is visible because every provider is disabled, the panel shows one empty state pointing at the enabled setting. A section shows the provider mark, name, and the active account's plan label.
- R21. One card per account: name (bold; the imported account is named by its email, as added accounts are by default), a muted second line (the email when it differs from the name; else org or team; else omitted), active marker, a chevron for drill-in, and one rail per window in kind order session, weekly, monthly, billing-period, model-scoped, unknown kinds after, label ascending within a kind, each with label, filled rail for `used`, an integer percent using R16's rounding rule, and a reset countdown at minute resolution, re-stamped every 30 s while the panel is open. Hovering a rail swaps its countdown for the exact reset time in the local timezone, with the timezone named. Balances render as a draining gauge: remaining always; funded and spent when the record carries them; nothing invented otherwise. A card with status `no-limits` shows one explanation line instead of rails. A window whose reset time is in the past reads "resetting" and queues one refresh of that account per window identity and reset timestamp, still subject to the 60 s per-account floor (R6), and does not queue again until a successful record changes or removes that reset; it never counts down negatively.
- R22. Set active is Enter, Space, or a click on the card body. Open terminal is a visible card action and the `o` key (R13a). Rename, sign in again, and remove live behind a pencil affordance as in World Clock; remove additionally confirms; the pencil holds nothing else.
- R23. "+ Add account" ghost button at the end of each provider section whose CLI is installed; hidden (and `a` ignored) on a `not-installed` section.
- R24. Drill-in: a per-account detail view (all windows large with exact reset times, identity details, home path, last status and help line, shared-entry health from R8). Transition: list cards slide and tilt away, detail fades in; reverse on Escape or Back. 140 ms OutCubic, no other motion. While drill-in is open the card-list bindings are suspended and j/k scroll.
- R25. Every status in section 4 maps to a designed state, never blank: `ok`, `not-installed`, `not-signed-in`, `expired`, `rate-limited`, `offline`, `failed`, `no-limits`. The pre-first-record loading state shows skeleton rails. Stale data is shown with its age, never hidden.
- R26. Keyboard, complete, using the shell's panel key catcher: opening the panel focuses the active card of the first enabled and installed provider that has a card, else the first focusable row; j/k and Down/Up walk every card in visual order across sections; h/l and Left/Right jump to the first card of the previous or next section; Enter and Space set active; d opens drill-in (the chevron is the mouse route); o opens a terminal for the focused card's account; r refreshes every saved account (R18 floor); a adds an account to the focused section; e opens the focused card's pencil menu (a cursor surface holding rename, sign in again, and remove with its confirmation; no other card actions exist; while it is open the card-list bindings are suspended, j/k move, Enter activates, Escape closes); Escape backs out of drill-in or the pencil menu, else closes; Tab moves to the neighboring bar panel; the key catcher's delete signal is not connected (remove is only reachable through the pencil and its confirmation). Every interactive row is a shell cursor surface with the standard focus ring.

### 6.5 Settings
- R27. Settings live inline on the widget's bar entry in shell.json and are editable with `omarchy bar set`: `refreshIntervalSec`, `warningThreshold`, `criticalThreshold`, `readout` (boolean), `readoutScope`, `providerOrder` (array of provider ids; unknown ids ignored, unlisted ids appended in id order) and `providerEnabled` (object of id to boolean), each nested value written as one JSON value. Defaults: refresh interval 900 s (minimum 60 s), warning 0.75, critical 0.90, readout on, `readoutScope` `active`, `providerOrder` `["claude","codex","grok"]`, every provider enabled when absent. Validation: a value of the wrong type or an unknown enum is replaced by its default; an interval below the minimum is clamped; thresholds are clamped to 0..1 and, if warning exceeds critical, warning is set equal to critical; duplicate provider ids keep the first occurrence. Defaults are also defined in QML because the shell does not read manifest defaults.

### 6.6 Security and privacy
- R28. Tokens never appear in records, caches, logs, tooltips, process arguments, process environment, or QML property dumps. The only files that hold tokens are the credential files inside homes and their descriptor-named refresh and transaction temp files, all 0600, the temp files existing only while an operation is in progress and removed on commit, abort, and startup recovery. `~/.config/omarchy/agent-desk/` and `~/.local/state/omarchy/agent-desk/` are 0700; data files Agent Desk writes there are 0600; routing shims are 0755; files a CLI writes inside an isolated home keep the CLI's own modes.
- R29. Agent Desk's own network calls are limited to the providers' usage, identity, and token-refresh endpoints, each with that provider's own credentials, sent in headers or request bodies, to `https://` URLs held as constants (R2). Collectors never disable TLS certificate verification and never follow redirects: any 3xx is `failed` and no second connection is made. Calls made by an invoked CLI are the CLI's.
- R30. Command routing writes only under `~/.local/bin` and the user-level shell or mise configuration location the plan chooses for PATH precedence, never replaces an unmarked file, and removes only what it created (R13).
- R31. Every non-literal UI string (provider or credential-file values, account names, home paths, settings-derived labels, command output) is rendered as plain text, never as rich or auto-detected text, so a crafted value cannot trigger a remote fetch or markup.

### 6.7 Packaging and testing
- R32. Installs with `omarchy plugin add <git url> --enable`, passes `omarchy plugin validate`, runs on Omarchy 4.0.0.alpha (manifest schemaVersion 1), needs nothing beyond bash, jq, python3, and curl from the base system. All collectors ship inside the plugin.
- R33. Hot-reloads while editing; README documents install, update (with the `omarchy restart shell` note), routing install and removal, the refresh race note from R5, what account-state entries do not stay in sync (R8), that hooks, plugins, and skills linked from the default home execute in isolated homes with that account's credentials, that routing-launched sessions do not repair missing shared entries, that a provider session may outlive a best-effort logout, and data locations.
- R34. Every collector runs against a fixture home plus canned responses with no network, and the test suite exercises every status in section 4 for every provider. Collectors and the runner read the clock, the floor, and the interval from an injectable source in tests; fixtures set timestamps; no acceptance test waits on wall-clock time.

## 7. Acceptance criteria

Automated (fixtures, fake CLIs, canned responses):
- A1. Each provider section shows exactly the windows and identity its fixture declares, with `used` normalized to 0..1 regardless of the fixture's scale, and kinds ordered session, weekly, monthly, billing-period, model-scoped, then label ascending. For Claude, a payload with values above 1 and one with fractions produce the same `used`; a Grok payload with every value at or below 1 is still read as points; a value above 100 clamps to 1.
- A1b. Balance fixtures: remaining 5 with no funded or spent gives `used` 0 and a gauge showing remaining only; remaining 0 gives `used` 1; funded 10, spent 4, remaining 6 gives `used` 0.4; the bar readout includes that value; a fixture with unit "USD" and precision 2 renders "6.00 USD" and one without unit renders "6 credits"; funded 0, spent 0, remaining 0 gives `used` 1 with no error.
- A2. A fake provider added as one descriptor plus one collector appears in the panel with no QML change.
- A3. With a canned refresh endpoint, a token expired for 10 minutes or more in an isolated home is refreshed once, written back at 0600, and the fake CLI in that home reads the new token. A token expired for any shorter duration is not refreshed. With the credential file's bytes changed but mtime unchanged between run start and the locked re-read, no refresh request is made. With an incomplete temp file pre-existing, no request is made in that run, the leftover is gone afterward, and the status is `expired`/`deferred`; with the temp file unwritable, no request is made. The replaced credential file is mode 0600. Refresh outcomes map as in section 4: a 401 fixture gives `expired` with Sign in again; unreachable gives `offline`; 429 gives `rate-limited`; timeout, 5xx, malformed body, and any 3xx each give `failed` with no second request; the fixture token is never sent anywhere but the constant origin, and every one of these enters backoff. Every failed-refresh fixture leaves the credential bytes unchanged; only 401, 403, or `invalid_grant` gives `expired` with reason `grant-rejected` and Sign in again; a local abort gives `expired` with reason `deferred`, no Sign in again, and no backoff.

- A5. Routing install then removal leaves `~/.local/bin` and the PATH configuration byte-identical to before. If the shim was replaced by a file without our marker, removal leaves it and reports. Removal deletes every marked shim. With the home variable set explicitly in the environment, the shim execs the real CLI with that home. With the shim's own directory first on PATH and no other binary of that name, the shim exits non-zero without re-entering itself. With plugin state naming the saved imported default home, the shim runs the real CLI with that home. With plugin state naming a path that is neither that nor a saved isolated home (including a homes path containing `..` or a symlink that resolves elsewhere), the shim execs the real CLI unchanged. Install against an unmarked existing shim target or fragment refuses as a whole, writes nothing, and leaves it untouched, also when the conflict is on the second target; installed shims are mode 0755; install with a provider CLI absent creates no shim for it.

## 8. Constraints

- Quattro bar-widget plugin: QML for widget and panel using the shell's `qs.Ui` kit and `Style`/`Color` tokens; no hand-rolled meters or buttons where the kit has one.
- Collectors are bash or python3 scripts bundled in the plugin; no compiled binaries in v1.
- The stock `omarchy.agents` widget may coexist; we do not disable or modify it.
- The 4.0.0.alpha shell does not read manifest `defaults`/`schema`; defaults live in QML too.
- No symlinks inside the plugin folder (validator rejects them). Symlinks inside isolated homes are fine; they are outside the plugin folder.
